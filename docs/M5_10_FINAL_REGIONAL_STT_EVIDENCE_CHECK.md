## 2. Current SpeechRecognition implementation

Source: `frontend/src/hooks/useSpeechRecognition.ts`.

- selected Kannada language maps to `kn-IN`;
- `continuous = false`;
- `interimResults = false`;
- `onresult` reads one result and trims the final transcript;
- a non-empty final transcript is sent as `{ action: 'user_message', text: transcript }`;
- interim transcripts are not captured or displayed;
- multiple recognition events are not concatenated;
- `onend` clears the recognition instance and listening state;
- changing the React `language` dependency creates a new callback for subsequent starts, but this hook contains no transcript/session-generation correlation;
- browser errors are surfaced, but there is no persisted raw STT event log.

Therefore the current infrastructure cannot prove whether either Kannada string came from Chrome, whether interim and final text differed, or whether a transcription was changed between recognition and backend dispatch. It can only prove behavior when a real browser instrumentation run captures those events; no such evidence exists in the repository.

Interpretation:

- Mapping `ಸಚಿವರು → HOD` is **UNPROVEN** and currently **UNSAFE**. “Minister” is not automatically a department-head query, and no product-approved meaning or live STT evidence exists.
- Mapping `ಸಂಖ್ಯೆ → Data Science` is **UNPROVEN** and **UNSAFE**. It would be a global semantic guess with no evidence that the word is an ASR substitution for Data Science.
- Recognizing `TechVidya` plus a Malayalam grammatical suffix at the event entity boundary is **SAFE in principle**, because it can be constrained to the known event name and preserve the canonical `events.techvidya` unit. It must not become a global fuzzy matcher.

## 5. Minimal fix design decision

The Kannada evidence is insufficient to authorize any production mapping. Stop before implementation. The next valid evidence step is one controlled real Chrome run that records, in order:

`Tap to Speak click → recognition.lang → onstart → interim results → final result → exact user_message payload`

Only if the exact strings are captured from that run should product owners decide whether they are accepted ASR substitutions. If approved, the eventual design should require department context plus a leadership/person question and use an explicitly approved substitution table; it must not globally map either word.

For Malayalam, a bounded event-name matcher for `TechVidya` with Malayalam suffix handling is the smallest safe design. It should emit only `events.techvidya`, preserve all existing ordered items, and leave general Malayalam parsing untouched.

## 6. Required regression tests for later implementation

- capture and assert raw `kn-IN` final transcript provenance in a real-browser harness;
- retain exact parser tests for both Kannada strings, but mark them as pending/approved product semantics rather than silently treating expected HOD output as proven;
- contextual tests for approved `ಸಚಿವರು`/`ಸಂಖ್ಯೆ` substitutions, including negative cases without a department/person context;
- Malayalam `TechVidya`, `TechVidyaയെ`, spacing, and punctuation variants at the event boundary;
- exact Kannada HOD, fees, TechVidya, and all-three ordered units;
- Hindi, Tamil, Telugu, Malayalam, and Romanized Kannada canonical cases;
- no-destruction partial-resolution tests;
- English false-positive tests proving unrelated uses of broad words do not trigger HOD or Data Science.
